The API Integration Model

This lesson covers exactly what happens when ThreatAware "integrates" with a tool — technically. After this, you can hold a first-round conversation with a prospect's engineer without bluffing.

1. Two Directions of Data Flow

ThreatAware integrations run in two directions:

DirectionWhat it meansExamples
Inbound (pull) ThreatAware calls the source tool's API to read data CrowdStrike → ThreatAware, Lansweeper → ThreatAware, Intune → ThreatAware
Outbound (push/action) ThreatAware sends data or triggers actions in another tool ThreatAware → Autotask (create ticket), ThreatAware → ServiceNow (raise incident)

The vast majority of integrations are inbound pulls. ThreatAware is the consumer of your tools' APIs, not the publisher. Outbound actions are mostly limited to ticketing / workflow tools.

Authentication

Each source tool uses its own auth mechanism. ThreatAware supports the common patterns used by SaaS security tools:

  • API key — most common; the customer generates a read-only key in the source tool and pastes it into ThreatAware
  • OAuth / client credentials — used by tools like Microsoft Intune / Azure AD
  • Username + password + MFA — some legacy tools
Talking point for engineers
ThreatAware recommends creating a dedicated read-only service account or API key with minimum required permissions in each source tool. It never needs write access to those tools to function. This is a security best practice and a common concern engineers raise.

What Gets Pulled

The specific data fields ThreatAware reads depend on what the source tool exposes, but across integrations the platform is always looking for the same core entities:

  • Devices / endpoints: name, OS, last seen, IP, MAC, serial, coverage state
  • Users: identity, associated devices, groups
  • Alerts: threat detections, severity, status, affected asset
  • Patch / vulnerability data: CVEs present, last patch date, missing patches

3. ThreatAware's Own API (Outbound to Customers)

ThreatAware also exposes its own REST API, which customers and integrators can call to read the unified data ThreatAware has assembled.

CharacteristicDetail
ProtocolREST over HTTPS
AuthAPI key (generated in the ThreatAware portal)
Access typeRead-only — the API returns data, it does not accept writes or trigger changes
Core data entitiesDevices, Users, Alerts, Integration-specific data
FormatJSON responses
Documentationapidocs.threataware.com

A typical use case: a customer's SOC team writes a script that calls ThreatAware's /devices endpoint to pull an up-to-date asset list into their SIEM or CMDB. Because ThreatAware has already done the correlation work, they get a clean, deduplicated list rather than raw noise.

What engineers ask about the ThreatAware API

Common first-round engineering questions and the honest answers:

QuestionAnswer
"Is there a webhook / real-time push?" The API is poll-based (read). Real-time alerting happens within the ThreatAware UI and via connected ticketing tools. Direct webhooks to arbitrary endpoints should be confirmed with ThreatAware's technical team.
"Can I write back to ThreatAware via API?" The current public API is read-only. Actions (like creating tickets) are handled through outbound tool integrations configured in the platform, not direct API writes.
"How often is data refreshed?" ThreatAware polls each source integration on a schedule. The exact cadence varies by integration type. Real-time connectors exist for some tools; others are hourly or daily. Confirm specifics with ThreatAware for a given integration.
"What about data residency / GDPR?" Worth flagging to ThreatAware's technical team — this is a deal-stage question, not a pre-sales blocker to resolve alone.
